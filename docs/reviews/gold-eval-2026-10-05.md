# Gold-standard eval: two models build a mockup from its picture

Run on 2026-10-05 with `pnpm eval:gold` (`apps/server/eval/run-gold-eval.ts`). Each model gets its own real Socrates server, an empty folder and the picture of a task board (`apps/server/eval/gold/task-board.webp`). It must scaffold a React and TypeScript app with the interactive `npm create vite@latest` wizard, install packages, run the dev server, open the page through the Playwright MCP server, compare it with the picture and fix it, with nobody stepping in. Afterwards the script opens the page in its own browser and checks it.

| | DeepSeek Flash (`deepseek-flash`, direct) | GLM 5.3 Flash (`z-ai/glm-5.3-flash`, OpenRouter) |
|---|---|---|
| Thinking level | High | High |
| Time | 10 min | 14.3 min |
| Tool calls (errors) | 108 (3) | 44 (2) |
| Interactive wizard answered in a real terminal | yes | yes |
| Terminal runs / inputs typed or pressed | 41 / 5 | 6 / 4 |
| Edits | 31 | 7 |
| How it looked at the page | Playwright `browser_take_screenshot` ×2, which it saw | Playwright `browser_run_code_unsafe` ×4 to write screenshots to files, then `read` ×6 on them |
| Expected labels on the page (48) | 48 | 48 |
| Search filters, tabs switch, checklist ticks, New task adds | 4 of 4 | 4 of 4 |
| Console errors | none | none |
| How the turn ended | `tokens`: the 5,000,000-token turn budget ran out | `final`: it chose to finish |

Both pages match the picture closely in layout, spacing, colours, text, numbers, tags, progress bar and checklist (side by side: `.socrates/evals/gold/<model>/compare.png`). DeepSeek downloaded four portrait photos for the avatars; GLM drew initials ("a deliberate substitution", it said). Neither is pixel-identical: DeepSeek's page is a little larger than the picture, GLM's a little smaller.

## What the models did

- **DeepSeek** built the app, then looked at it through the browser tool: after its first screenshot it said the page was already very close and that the viewport was smaller than the picture, resized the browser to the picture's size, took another, and then measured the picture and its own page pixel by pixel with Python (Pillow, fontTools) to correct font sizes and spacing. It was stopped by the token budget in the middle of that pass and its final answer said so plainly: partly done, the last edits not yet re-checked, interactions not yet exercised. Its page did in fact pass every check.
- **GLM** built the app and a Board, List and Timeline view, ticked, searched and added through the browser, fixed its Timeline labels, ran lint and a build, and finished with an accurate summary.

## Harness problems the eval found

Fixed in this change, each with tests:

1. **An MCP screenshot reached the model as one line of text** ("[image image/png, about N bytes]"). It now reaches a model that can see as an image (first 4 of a result, each up to 5 MB, the bytes deciding the format); a model that cannot see is told its content is unknown. The ledger keeps only how many were shown. Many screenshots add up, so past 8 in a turn the oldest go down to 4, a batch at a time. DeepSeek's reasoning in the run shows it did see its screenshots.
2. **`terminal_control wait` could sit idle for its whole 10-minute cap at a prompt.** A model that waits for `exit` on a wizard was never told the wizard had asked a question. Both models lost 10 minutes per question this way, twice over, before the fix. A wait on a PTY session now ends with `input_required` as soon as the program asks.
3. **Menus were not recognised as waiting for input.** The old rule (idle and an unfinished last line) misses `npm create vite`, whose last line is finished; a menu hides the terminal's cursor while it waits for a key, which the harness now notices (checked against the real wizard). Writing to a session also marks its prompt answered until it prints again.

Fixed afterwards, at the user's request:

4. **The turn token limit ended DeepSeek's turn.** `maxTokens` (5,000,000) summed every request's whole prompt, cache reads included, so a 100-call turn with a 50,000-token context reached it after ten minutes of good work. A request now counts its prompt without cache hits, the cache read at a tenth (the weight providers charge about), and its output; the default is 20,000,000. Checked against DeepSeek's real usage report (3,840 of 4,012 prompt tokens served from cache on a repeat). The step (200) and time (60 minutes) limits are unchanged.

Found, not fixed (proposed for the first trial round):

- **Reading a screenshot file outside the project asks for approval** (GLM was asked twice for `shots/` and its parent). That is correct under "My folders", but a browser tool's own output folder is an obvious thing to allow; consider letting `read` open a folder an MCP server was configured to write to.
- **Relative paths inside an MCP server resolve against Socrates' working directory.** GLM's `shots/board.png` landed in the repository root until the eval gave the server its own `cwd`. Worth a line in the MCP documentation, and a default.
- Slow starts: the first message spent about 25 seconds on routing with DeepSeek Flash as the router, and the wizard needed many round trips. The new "Reading your message" and "Thinking" line makes the wait visible.

## Where everything is

All of it is under `.socrates/evals/gold` (about 1.1 GB with both runs, a first GLM run without a working browser tool, the npm caches and the browser tool): data homes, projects, transcripts (`transcript.jsonl`), pictures, `results.json`. `pnpm eval:gold --clean` deletes it all, and nothing the eval creates lives anywhere else.

A first attempt, stopped after 21 minutes, had pointed the browser tool's temporary folder deep inside the eval folder, which made its local sockets too long (`Socket directory path is too long`), so that run never used the browser tool and GLM fell back to installing puppeteer; it is kept as `glm-run1` and built a similar page.
